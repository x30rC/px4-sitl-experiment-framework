# Руководство по запуску

[Содержание](README.md) · [Установка](INSTALL.md) · [Код](ARCHITECTURE.md)

## Консольное меню и чистый полёт

Запустите `python3 run_test.py` **в терминале WSL** без аргументов: появится
ASCII-антенна и меню. Цвет включается только в терминале (переменная
`NO_COLOR` отключает его). Пункт `1` запускает миссию **без процессов подмены**;
длительность наблюдения задаётся в секундах (по умолчанию 60). Пункт `2`
позволяет выбрать `gps`, `imu`, `mag`, `baro` или их сочетание через запятую,
затем настроить выбранные датчики. После завершения сценария меню появляется
снова. `0` или Ctrl+C во время выбора закрывают меню.

В пункте `2` датчики можно указать именами (`gps,mag`) или номерами (`1,4`).
Затем выбирается режим времени подмены для всех выбранных датчиков:
`sync` — длительность и фазы GPS отсчитываются по Gazebo clock, IMU/mag/baro
по timestamp входных сообщений; пауза симулятора останавливает таймеры.
`async` — фазы и длительность всех датчиков идут по независимым монотонным
часам процесса. Даже в async IMU/mag/baro подменяют **только поступающие**
из Gazebo сообщения, а не создают новые без входного потока. При отсутствии
Gazebo clock или исходных сообщений тест завершается с ошибкой, а не считается
успешным (в том числе при паузе симулятора более 15 секунд). Пример:
`python3 run_test.py --non-interactive --spoof-sensor gps,imu,mag,baro --time-mode sync`;
для независимых часов замените `sync` на `async`. По умолчанию при CLI-запуске
используется `async`.

При собственном запуске PX4 каждый прогон использует отдельный `GZ_PARTITION`,
чтобы PX4 не подключился к топикам Gazebo, оставшимся от предыдущего прогона.
После фиксированной начальной задержки сценарий дополнительно ждёт реальные
сообщения GPS и выбранных датчиков (до 60 секунд), прежде чем начинать миссию.
Если мир или потоки не появились, прогон завершается с диагностикой отсутствующих
датчиков; тайм-аут не следует устранять увеличением длительности самой атаки.

Для скриптов меню не используется: `python3 run_test.py --non-interactive
--spoof-sensor none --baseline-duration 60` запускает чистый полёт, а
`python3 run_test.py --non-interactive --spoof-sensor gps,baro` — полёт с
подменой. Для проверки без SITL добавьте `--dry-run`; для проверки без арминга
также добавьте `--skip-mission`. Чистый полёт заканчивается **по времени**,
а не по достижении последнего waypoint. При `--skip-px4` пользователь сам
отвечает за настройки внешнего PX4 и отсутствие сторонних процессов подмены.

Все примеры предполагают установленный стенд из [INSTALL.md](INSTALL.md) и каталог `~/_spoof_gaz`; для другой копии используйте её путь. Работайте только со **своим** PX4 SITL, не с физическим аппаратом. `run_test.py` сам подбирает Linux venv; отдельные `gps_publisher.py` и `imu_publisher.py` можно проверять через системный `python3`, если Gazebo bindings установлены системно.

## Перед первым запуском

```bash
cd "$HOME/_spoof_gaz"
python3 gps_publisher.py --check
python3 imu_publisher.py --check
python3 run_test.py --non-interactive --dry-run --spoof-sensor gps --skip-mission
```

`--dry-run` проверяет конфигурацию и показывает команды, но **не запускает** Gazebo и не подтверждает, что миссия полетит. При первом настоящем запуске убедитесь, что нет другого ручного экземпляра PX4/Gazebo: сценарий может завершить оставшиеся процессы симуляции **текущего пользователя**.

## Безопасная ступенчатая проверка

1. Без миссии, с короткой публикацией GPS (нет арминга):

   ```bash
   python3 run_test.py --non-interactive --spoof-sensor gps --skip-mission \
     --intensity 0 --duration 3 --wait-after-spoof 0
   ```

2. Короткий запуск штатной миссии с GPS на опорных координатах (интенсивность `0 %`, **не гарантирует** равенство координат реальному GNSS модели):

   ```bash
   python3 run_test.py --non-interactive --spoof-sensor gps \
     --intensity 0 --duration 5 --wait-after-spoof 1
   ```

   Ищите **подтверждения** `PX4 готов к армингу`, `Миссия загружена` и `режим MISSION`. Код завершения `0` подтверждает сценарий, а не завершение **всего** полётного задания: через пять секунд аппарат может ещё набирать высоту.

3. Только затем задавайте смещение. Интерактивно: `python3 run_test.py` и ответьте на вопросы (тип сенсора: `1=GPS`, `2=IMU`, `3=GPS+IMU`, `4=mag`, `5=baro`). Без вопросов используйте `--non-interactive`.

## Повторения с различными маршрутами

Для серии независимых запусков (PX4 и Gazebo перезапускаются перед каждым):

```bash
python3 run_test.py --non-interactive --spoof-sensor both --repeats 10 \
  --route-min-m 400 --route-max-m 800 --route-seed 42 \
  --duration 240 --imu-duration 240 --wait-after-spoof 5
```

`--repeats` принимает 1..100; по умолчанию 1, исходный `mission.plan` без изменений.
При `--repeats 2` и более создаётся отдельный QGC Plan для каждого прогона:
в исходном плане изменяется **только конечный waypoint**, высота и взлёт
остаются прежними. Направления выбираются из разных угловых секторов, расстояние
от planned home — из заданного диапазона (по умолчанию 400..800 м;
разрешено 100..2000 м). Для одного случайного маршрута используйте
`--random-mission`. Без `--route-seed` выбирается новый seed, он печатается в
консоли; указанный seed даёт повторяемые координаты при том же шаблоне и
числе прогонов. `--dry-run` показывает все маршруты, ничего не запускает.

Каждый прогон при собственном PX4 создаёт отдельный `logs/<дата_время>_<имя ULog>.csv`;
после успешной конвертации временная папка с ULog удаляется. Если конвертация
не удалась, ULog и, для случайного маршрута, использованный `mission.plan`
остаются в папке прогона для восстановления. Для автоматического экспорта нужны
`pandas` и `ulog2csv` (`pyulog`) в окружении запуска. При ошибке запусков больше не будет. Повторы несовместимы
с `--skip-mission` и `--skip-px4`: внешний PX4 нельзя надёжно сбросить между
попытками. Генератор рассчитан на текущий план: takeoff + **один** waypoint с
относительной высотой; неизвестный формат не переписывается молча.
При ошибке симулятора доступный ULog тоже конвертируется, если это возможно;
это **не** означает успешного полёта. Серия останавливается на ошибочном прогоне.

**Важно:** сценарий подтверждает старт миссии, но не подтверждает достижение
конечного waypoint. Он завершает прогон по длительности публикации: для дальних
маршрутов увеличивайте `--duration` и `--imu-duration` и проверяйте фактический
путь по ULog. Без проверки среды, препятствий, границ полигона и геозон
произвольные направления пригодны только для контролируемого SITL-стенда.

## GPS и периодические фазы

```bash
python3 run_test.py --non-interactive --spoof-sensor gps \
  --intensity 85 --rate-hz 75 --duration 60 \
  --active-seconds 5 --idle-seconds 4
```

`intensity=0` публикует опорную позицию, `100` — целевую; координаты и высоту можно переопределить `--reference-lat/lon/alt` и `--target-lat/lon/alt`. Формула: `reference + (target - reference) * intensity / 100`. Если оба значения `active/idle` равны нулю, публикация непрерывна; если оба положительны, действуют циклы активной фазы и паузы. Задавать только одно положительное нельзя. В паузе GPS publisher **не публикует** ложные сообщения, это не означает принудительного возврата к реальной позиции.

`gps_publisher.py` — самостоятельный публикатор: `python3 gps_publisher.py --dry-run --intensity 50` проверяет настройки без Gazebo, `python3 gps_publisher.py --duration 5 --rate-hz 20` публикует в штатный NavSat topic, если существует мир и модель. Самостоятельный запуск **не** загружает миссию и **не** запускает PX4.

## IMU

Полный IMU-режим доступен **только после применения и пересборки PX4 patch** из [INSTALL.md](INSTALL.md#4-патчи-px4-для-imu-mag-и-baro). Для знакомства с параметрами без симуляции: `python3 imu_publisher.py --dry-run`. Для проверки bindings: `python3 imu_publisher.py --check`.

```bash
python3 run_test.py --non-interactive --spoof-sensor imu \
  --imu-intensity 85 --imu-angular-z 0.8 --imu-rate-hz 75 \
  --imu-active-seconds 3 --imu-idle-seconds 2 --imu-duration 12
```

В режиме `run_test.py` файл `imu_publisher.py` не генерирует статический IMU вместо движущегося аппарата: он читает штатный топик Gazebo, пересылает **все** входные IMU сообщения в `/spoof_gaz/imu` и добавляет offset к части сообщений во время active-фазы. `--imu-rate-hz` задаёт частоту **применения offset**, не частоту пересылки baseline (~250 Гц у x500); в idle-фазе baseline продолжает идти. `--imu-angular-{x,y,z}` — смещения гироскопа в рад/с, `--imu-linear-{x,y,z}` — смещения акселерометра в м/с² при `100 %`. Векторы в Gazebo FLU, bridge переводит их в PX4 FRD. `imu_publisher.py --duration 5` **без** `--source-topic` — отдельный генератор, не равноценный полному relay-тесту.

## Магнитометр и барометр (x500)

В проекте доступны `--spoof-sensor mag`, `baro`,
`mag,baro` и сочетания с `gps,imu` (через запятую; `both` сохраняет старое
значение `gps,imu`). Relay передаёт исходные Gazebo сообщения до миссии и после
атаки, подменяя только измерения в активной фазе. При `--time-mode sync` фазы привязаны к штампу Gazebo; при паузе
симулятора время атаки не идёт. В режиме `async` используются монотонные часы.

Перед первым запуском соберите PX4 bridge с переключением подписок:

```bash
# Сначала примените оба патча по порядку из INSTALL.md, раздел 4.
# После применения патчей:
cd "$HOME/PX4-Autopilot"
cmake --build build/px4_sitl_default --target px4 -j2
```

```bash
cd "$HOME/_spoof_gaz"
python3 run_test.py --non-interactive --spoof-sensor mag,baro \
  --mag-z 0.00002 --baro-pressure-offset 150 \
  --mag-duration 30 --baro-duration 30 --time-mode sync
```

Магнитное смещение задаётся в **Tesla**, в координатах исходного Gazebo
`field_tesla`, давление — в **Pa** (положительное смещение воспринимается как
понижение высоты). `--mag-intensity`, `--baro-intensity` масштабируют смещение;
`--mag-active-seconds`, `--mag-idle-seconds`, `--baro-active-seconds`,
`--baro-idle-seconds` задают чередование. По умолчанию барометр получает
смещение **+100 Па**, магнитометр **+0.00002 Тл по Z**; для baseline явно
задайте `--baro-pressure-offset 0` либо `--mag-z 0`. Интерактивный режим
спрашивает интенсивность, длительность, величину смещения и периодичность
**отдельно для каждого выбранного датчика**. Например, ответ `5` в выборе
датчика теперь открывает настройки барометра; активная и пассивная фазы
задаются в секундах. В паузе relay передаёт исходное измерение, а не
останавливает поток датчика.

Таймер атаки baro/mag начинается с первого сообщения Gazebo **после**
подтверждения миссии и стабилизации; часы выбираются через `--time-mode`.
Если PX4/Gazebo перестал передавать сообщения, атака не может продолжаться:
сценарий завершается с ошибкой и сохраняет ULog, но не считает эксперимент
успешным. Сообщение `spoofed=0` означает, что подменённых измерений не было;
при нормально работающем стенде ищите `атака активирована` и
`опубликовано первое подменённое измерение`. Длительность в CLI задаёт окно
атаки, а `--wait-after-spoof` добавляет время записи baseline после неё.
Если графическое окно Gazebo нестабильно в WSL, можно запускать сервер без GUI:
`HEADLESS=1 python3 run_test.py` (сам Gazebo и физика по-прежнему работают).
Успешное завершение короткого теста подтверждает запуск миссии и подмену
измерений, **не** достижение конечной точки маршрута.
При обычном запуске миссии оркестратор также создаёт в Gazebo
`spoof_gaz_goal`: оранжевую сферу радиусом 5 м на высоте конечного waypoint
и тонкий столб до земли. Это **только визуальные объекты**, без столкновений;
сфера не управляет дроном и не гарантирует достижение цели. Координаты берутся
из реально загружаемого QGC-плана (в том числе случайного плана данного
повтора). В консоли ищите `Метка цели Gazebo`; при неудаче её создания
полёт продолжится с предупреждением. В `HEADLESS=1` метка существует в
мире, но окна Gazebo не будет. С `--skip-mission` маркер не создаётся.
PX4 запускается с `PX4_GZ_MAG_TOPIC=/spoof_gaz/mag` и
`PX4_GZ_BARO_TOPIC=/spoof_gaz/baro` автоматически. С `--skip-px4` переменные выбранных датчиков должны быть выставлены **до запуска внешнего PX4**
и присутствовать в окружении `run_test.py`; `GZ_PARTITION` обоих процессов
должен совпадать, если он задан. Не публикуйте
подмену на исходный топик датчика: это смешает реальные и ложные сообщения.
Проверяйте `sensor_mag`, `sensor_baro` и EKF innovations в ULog; наличие топика
Gazebo без подтверждения в PX4 не доказывает успешную подмену.

## Совместный режим

```bash
python3 run_test.py --non-interactive --spoof-sensor both \
  --intensity 85 --rate-hz 75 --active-seconds 5 --idle-seconds 4 --duration 20 \
  --imu-intensity 85 --imu-rate-hz 75 \
  --imu-active-seconds 5 --imu-idle-seconds 4 --imu-duration 20
```

Перед запуском миссии включается baseline IMU relay; после подтверждения `MISSION` он получает сигнал активации; затем начинается GPS-публикация. PX4 получает только выходной IMU-топик relay, **не** два конкурирующих IMU-потока. Если цель — только демонстрация публикации, добавьте `--skip-mission` (без полёта). `--skip-px4` предполагает, что PX4 уже запущен и что для IMU ему **заранее** задан `PX4_GZ_IMU_TOPIC=/spoof_gaz/imu`. Эта же переменная
должна присутствовать в окружении `run_test.py`; `GZ_PARTITION` обоих
процессов должен совпадать, если он задан.

## Миссия и логи

Файл `<каталог проекта>/mission.plan` — QGroundControl Plan; нельзя подменять его простым CSV. Сценарий отправляет GCS heartbeat, подключает MAVSDK к `udpin://0.0.0.0:14540`, ждёт position/home/armable, загружает миссию, армит и подтверждает режим `MISSION`. При неуспехе обязательной миссии сценарий завершается ошибкой, а не выдаёт ложное сообщение об успехе. `--mission-timeout 60` позволяет увеличить тайм-аут **каждого** шага MAVSDK при медленном запуске; `--skip-mission` отключает загрузку, арминг и heartbeat.

После запуска с собственным PX4 новый `.ulg` временно копируется в `<каталог проекта>/logs/<дата_время>_<имя ULog>/`. После конвертации CSV и три PNG сохраняются в `logs/`, а временная папка удаляется вместе с копией ULog и планом случайного маршрута. Если нужно хранить этот план отдельно, сохраните его до завершения прогона; CSV не содержит полной копии QGC Plan. При ошибке конвертации или создания рисунков папка и ULog сохраняются. При `--skip-px4` копирования и автоматической конвертации нет. Для проверки взлёта и состояния оценивателя анализируйте CSV и графики, а не только консоль. Графики сохраняются как файлы, GUI-окно автоматически не открывается (работает и без монитора).

Для автоматической конвертации нужны `pandas`, `matplotlib` и команда `ulog2csv` из `pyulog`; все они входят в `requirements.txt`. Ручная обработка оставшихся или старых ULog:

```bash
source ./venv/bin/activate
python3 consolidate_logs.py --help
python3 consolidate_logs.py --folder 2026-09-23_15_22_02 --dry-run
python3 consolidate_logs.py --folder 2026-09-23_15_22_02
```

По умолчанию обрабатывается `<каталог проекта>/logs`, можно указать `--logs-dir /абсолютный/путь/к/logs` и повторить `--folder` для нескольких экспериментов. Без `--folder` обрабатываются **все** подпапки; если результат для папки уже существует, она пропускается с ненулевым кодом завершения. Каждый ULog даёт **ровно один** `logs/<имя папки>_<имя ULog>.csv` с выровненными временными рядами и три картинки `logs/<имя папки>_<имя ULog>_{trajectory,altitude,diagnostics}.png`: маршрут (GNSS, оценка PX4, истина SITL при наличии), высота и диагностические показатели во времени. Если топик не записан, соответствующий график показывает «No data recorded». Ручная конвертация выполняется во временном каталоге: старые CSV не подмешиваются, исходные `.ulg` и папки **не удаляются**, готовые результаты **не перезаписываются**. `--dry-run` не требует зависимостей и ничего не записывает.

В CSV одна строка каждые 100 мс (`timestamp_us` — время PX4 в микросекундах, `time_s` — секунды с начала доступной записи). Поля с префиксом топика относятся к одному источнику, `<топик>.age_ms` показывает возраст его последнего сообщения; используется только сообщение **до или в момент** временной метки, не старше 500 мс. Устаревшие/отсутствующие измерения остаются пустыми; датафрейм не создаёт несуществующие топики. В анализ включены GNSS и качество фиксации, IMU/gyro/accel, ошибки и флаги оценивателя, координаты/скорость PX4, задания и состояние полёта, а также `*_groundtruth` при наличии в SITL.

Для GPS-смещений `gps_vs_truth.horizontal_error_m` сравнивает измерение GNSS с физической позицией симулятора, `estimate_vs_truth.horizontal_error_m` — результат навигации PX4 с ней же; различие показывает, попало ли искажение в оценку положения. `*.altitude_error_m` показывает вертикальное расхождение; `estimator_aid_src_gnss_pos.*` (innovation, test_ratio, fused/rejected) помогает проверить, принял ли EKF GNSS, а `vehicle_status.*` и `failsafe_flags.*` — возможные последствия для режима полёта. Для IMU сопоставляйте `sensor_gyro`, `sensor_accel`, `vehicle_imu`, `vehicle_angular_velocity`, `vehicle_angular_velocity_groundtruth`, `sensors_status_imu` и `estimator_aid_src_gravity`: изменения скорости вращения, несогласованность датчиков и инновации могут указывать на реакцию оценивателя. Это **диагностические признаки, а не автоматический детектор атаки**; часть потоков может не логироваться, сырой gyro/accel в обычном ULog может иметь редкую выборку. Числа можно интерпретировать только с учётом `age_ms`, наличия ground truth и условий конкретного испытания. Абсолютные локальные `x/y` из estimator и truth автоматически не вычитаются: их NED-истоки могут различаться.
Для конвертации активируйте окружение (`source ./venv/bin/activate`), чтобы команда `ulog2csv` была доступна; после этого можно использовать `python` из того же venv вместо `python3`. Если рабочий venv находится в соседней копии проекта, используйте путь к нему вместо `./venv`.

## Неполадки

| Сообщение / симптом | Действие |
| --- | --- |
| `Gazebo Python` не найден | [Установка](INSTALL.md#3-создание-собственного-виртуального-окружения): системные bindings + `--system-site-packages` |
| PX4 пишет `No connection to the GCS` | До начала миссии это возможно; после запуска heartbeat проверьте строку `GCS heartbeat запущен`, UDP `18570` и установленный `pymavlink` |
| `Тайм-аут MAVSDK` / после `GCS heartbeat` нет ответа | Проверить PX4/Gazebo, UDP `14540`, процессы другого запуска; увеличить `--mission-timeout`; отсутствие GUI само по себе не доказывает, что PX4 не запущен |
| `gazebo already running world: default` | Найдите другой экземпляр, завершите **свой** ручной запуск; скрипт очищает stale-процессы текущего пользователя перед управляемым запуском |
| IMU: `STALE`, `TIMEOUT` или нет `using IMU topic override` | Пересоберите патченный PX4, убедитесь, что relay запущен и source/output topics совпадают с моделью |
| `mission.plan` отсутствует | Поместить план рядом с `run_test.py` либо добавить `--skip-mission` |
| Ошибка периодического режима | Установить **оба** значения `active/idle` > 0, либо оба равными 0 |

Полная справка: `python3 run_test.py --help`, `python3 gps_publisher.py --help`, `python3 imu_publisher.py --help`, `python3 sensor_relay.py --help`.
